# eSIM-коробка: продуктовый анализ

Академическое (референсное) решение — «коробка» личного кабинета мобильного eSIM-оператора на стеке youndie: petich, kompot, katcher, metrik, tracy, booblik. Сервер — Kotlin/JVM (Ktor), клиент — Compose Multiplatform (Android + iOS). Всё за границей системы (BSS, SM-DP+, платежи, SMSC) мокается.

## 1. Что это и зачем

**Продукт**: white-label личный кабинет абонента eSIM-оператора (MVNO). Оператор берёт коробку, брендирует и получает приложение + сервер без разработки клиента.

**Академическая цель**: интеграционная витрина стека — каждая библиотека занимает ту роль, ради которой написана, и телеком-домен нагружает их естественно, без искусственных примеров.

**Ключевой продуктовый тезис**: благодаря backend-driven UI (kompot) новые экраны, акции, тарифы и брендинг доезжают до абонента **без релиза приложения**. Для «коробки» это главная ценность: кастомизация оператора = конфигурация сервера, а не форк клиента.

## 2. Пользователи и сценарии

Один тип пользователя — **абонент**. (Админка оператора — за рамками v1, упоминается в roadmap.)

Сценарии по частоте:

1. Посмотреть баланс и остатки (ГБ / минуты / SMS) — ежедневный сценарий, главный экран.
2. Пополнить баланс (mock-платёж).
3. Купить пакет: базовый из каталога или лёгкий кастом (выбрал ГБ/мин/SMS — увидел цену — подтвердил).
4. Заказать и установить eSIM (QR / activation code), посмотреть статус и детали своих eSIM.
5. Сменить тариф.
6. Роуминг: узнать статус/зону, купить роуминг-пакет перед поездкой.
7. История операций: списания, покупки, активации.

## 3. Функциональный объём

### v1 (ядро)

| Область | Что входит |
|---|---|
| Авторизация | Номер + OTP (SMS мокается), сессия через kompot-auth |
| Баланс | Текущий баланс, пополнение (mock-шлюз), история операций |
| eSIM | Список eSIM абонента, статусы (ordered → ready → installed → active → suspended/terminated), детали (ICCID, QR, activation code), заказ новой eSIM (wizard) |
| Тарифы | Текущий тариф, каталог, смена тарифа с подтверждением |
| Пакеты | Остатки по счётчикам (ГБ/мин/SMS) с прогрессом; базовые пакеты из каталога; лёгкий кастом-конструктор (3 слайдера + динамическая цена) |
| Роуминг | Статус роуминга, зоны/страны, роуминг-пакеты |

### Отложено

Физические SIM (модель это предусматривает: Esim — подтип Sim), семейные аккаунты, автоплатёж, админка оператора, перенос номера (MNP), нативный SwiftUI-клиент через kompot-swift-interop.

### Границы системы — что мокаем

| Внешняя система | Мок |
|---|---|
| BSS/OCS (биллинг, счётчики) | In-memory/Postgres мок: тарификация не считается, счётчики декрементируются по фиктивному «трафику» шедулером |
| SM-DP+ (выпуск eSIM-профилей, GSMA RSP) | Генератор ICCID + фиктивный `LPA:1$...` activation code и QR |
| Платёжный шлюз | Всегда-успех / настраиваемый отказ / задержка — чтобы демонстрировать компенсации саг |
| SMSC (OTP) | Код пишется в лог/отдаётся в dev-эндпоинте |
| HLR/HSS, сеть | Не моделируется, статусы меняются сагами |

## 4. Доменная модель

Subscriber (msisdn, name) → Account (balance, currency) → Sim/Esim (iccid, status, activationCode) → TariffPlan (базовые квоты, цена/мес) → Package (base | custom; квоты ГБ/мин/SMS, срок, зона: home | roaming-zone) → UsageCounter (тип, лимит, остаток, период) → Order (покупка пакета/eSIM/смена тарифа; статусная модель = состояния саги) → Transaction (списание/пополнение).

Order — центральная сущность: каждая покупка и смена тарифа — это сага petich, и статус заказа в UI отражает фазу саги, включая «ожидает подтверждения» и «отменён (компенсирован)».

## 5. Раскладка по стеку

| Библиотека | Роль в коробке | Что именно используется |
|---|---|---|
| **kompot** | Весь UI-контракт: сервер описывает экраны, CMP-клиент рендерит | `kompot-core/standard/client`; `kompot-forms` + `form-standard` — конструктор пакета и формы; `kompot-wizard` — заказ eSIM и смена тарифа; `kompot-theme` + `kompot-ds-material` — white-label темизация с сервера; `kompot-auth` — сессия после OTP; `kompot-realtime` (+server) — живое обновление остатков и статуса заказа; `kompot-client-cache` — офлайн-кэш экранов; `kompot-analytics` — импрессии/действия; `kompot-spec` + TCK — контроль контракта в CI; кастомные компоненты приложения: карточка остатков, QR-компонент, карточка eSIM (через `@KompotComponentMarker`) |
| **petich** | Все многошаговые операции с деньгами и внешними системами | Сага «покупка пакета»: резерв средств → активация в mock-BSS → списание → событие; сага «заказ eSIM»: списание → запрос профиля в mock-SM-DP+ → выдача QR; сага «смена тарифа». `Suspend` — подтверждение покупки (OTP/confirm) с TTL и авто-откатом; `petich-idempotency` — повторные платежи; `petich-postgres` + outbox — события в одной транзакции с состоянием; `petich-scheduler` — ежемесячное продление тарифа, сгорание пакетов |
| **booblik** | Шина событий между сервером и потребителями | Топики `orders`, `usage`, `notifications`: outbox petich публикует в booblik; consumer-ы — нотификатор (пуш в realtime-канал kompot) и «симулятор трафика», декрементирующий счётчики |
| **tracy** | Структурные логи и трейсы | `traceparent` через все вызовы; entity keys: `msisdn`, `iccid`, `orderId` — «покажи всё, что происходило с заказом» при разборе демо-инцидента |
| **metrik** | Метрики Ktor-сервера | RPS, ошибки, латентность по роутам, деплой-маркеры, алерты в Telegram |
| **katcher** | Крэши | Серверные ошибки + Android-клиент (Gradle-плагин, mapping), breadcrumbs = переходы по экранам |

Демо-достоинство связки: один сценарий «купил пакет» проходит через kompot-форму → сагу petich → outbox → booblik → realtime-обновление экрана, и виден целиком в tracy по `orderId`, в metrik по латентности, а падение — в katcher.

## 6. Архитектура (кратко)

- **Сервер**: один Kotlin/JVM-процесс (Ktor) + Postgres + booblik-брокер. Внутри — модули: screens (kompot-роуты), domain (заказы/саги), mocks (BSS, SM-DP+, платежи, SMSC).
- **Клиент**: Compose Multiplatform (Android, iOS), тонкий: kompot-client + реестр кастомных рендереров (остатки, QR, eSIM-карточка) + katcher + навигация `kompot-navigation`. Бизнес-логики в клиенте нет — только формы (form-core валидирует локально) и рендеринг.
- **Наблюдаемость**: metrik + tracy + katcher — три отдельных self-hosted бинаря, поднимаются docker-compose рядом.

## 7. Риски и ограничения

- Backend-driven UI ограничивает дизайн: экраны собираются из компонентного словаря; уникальный экран = новый компонент в реестре и релиз клиента. Словарь надо зафиксировать рано (см. бриф дизайнеру).
- iOS: Compose Multiplatform покрывает UI, но QR/установка eSIM в реальный eSIM-стек ОС не идёт (мокаем — показываем QR, «установку» имитируем).
- booblik — один процесс без репликации: для демо это честно, для продакшн-коробки — заявленное ограничение.
- Снапшот-версии библиотек (`reposilite.kotlin.website/snapshots`) — фиксировать через kompot-bom и конкретные версии.

## 8. Метрики успеха (для академического проекта)

Сквозное демо «регистрация → установка eSIM → покупка кастом-пакета → откат по таймауту подтверждения» проходит на обеих платформах; kompot-TCK и client-TCK зелёные в CI; каждый из шести компонентов стека задействован по своему прямому назначению и это видно в наблюдаемости; смена бренда (тема + тексты) — без пересборки клиента.

## 9. Roadmap

1. **M0** — mock-сервер + kompot-экраны: логин, главная, остатки; CMP-клиент рендерит.
2. **M1** — саги petich: покупка пакета с подтверждением и компенсацией; история операций.
3. **M2** — booblik + realtime: живые остатки, симулятор трафика; wizard заказа eSIM с QR.
4. **M3** — роуминг, кастом-конструктор, темизация вторым брендом.
5. **M4** — наблюдаемость в docker-compose (metrik/tracy/katcher), TCK в CI, демо-сценарий инцидента.
6. **Далее** — физические SIM, админка оператора, SwiftUI-клиент.
